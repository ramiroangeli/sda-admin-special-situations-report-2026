# Steve Review App

Private, single-reviewer web app for Steve's commercial review of the active
**Specialist Disability Accommodation Administration & Special Situations Report
2026** (`SDA-ADMIN-2026`). Five open review items, one decision each (Approve /
Change / Remove / Needs more evidence), autosaved to Supabase, exportable to
JSON/CSV/DECISIONS.md.

This app lives at `04.review/app/` in the project's top-level structure. It is
separate from and does not modify `../../03.production/` (the report build
engine) or `../../02.content/` (the editorial content) — it only reads from
them, at build time, via `scripts/generate_seed.mjs` and `scripts/copy_assets.mjs`.

## Architecture

- **Frontend**: Next.js 14 (App Router, plain JavaScript, no CSS framework) — deploys to Vercel.
- **Backend/persistence**: Supabase Postgres, accessed only from Next.js server-side API routes using the `service_role` key (never exposed to the browser).
- **Access control**: a single long-lived shared token per audience (Steve / QA), gated by Next.js Middleware, set as an httpOnly cookie. No account system. See "Access / security" below.
- **Content source**: `content/pages.yaml`-derived review data is generated once, at build time, from `../../02.content/review_manifest.yaml` (+ the same Steve-facing text trims used in `../../03.production/content/review_overrides.yaml`) into `src/data/review_items.json`. This is the only place the questions are authored — never hand-edit that JSON file.
- **Page previews**: the relevant page renders are copied from `../../03.production/out/page_renders/` into `public/page-renders/` at build time. The full public report PDF is copied from `../../05.outputs/public/` into `public/report/full-report.pdf` for the optional "View full report" link.

This is intentionally not a CMS — one Postgres table plus an audit-log table, no admin UI, no rich text editor, no user management.

> **Note on `src/middleware.js`'s location**: with a `src/` directory layout, Next.js requires the middleware file to live at `src/middleware.js`, not at the project root — putting it at the root silently disables it (no build error, no runtime error — it just never runs, which for an access-control file is exactly the failure mode you don't want). This was caught during local testing; documenting it here so it doesn't get "fixed" backwards later.

## Review model

The active review items are currently an empty list — read directly from
`../../02.content/review_manifest.yaml`, the project's single canonical
manifest (Q1, Q3, Q7, Q11 were resolved in the round-1 Steve review and
removed from that file; Q8/Q9 were retired earlier still — see
`review_manifest.yaml`'s own header comment for the full disposition history).
`Q5`/`Q6` both point at page 17 — they correctly show the same page preview,
since the preview is derived from `page_number`, not duplicated per question.

Each item shows: page number + title, topic, current working view, decision
required, the actual report page preview image, and — only when there's more
than one — the other pages a decision would affect (page numbers only). It
never shows claim IDs (`ADM-###-##`), evidence codes (`INT-##`/`PUB-##`), or
drafting-history text — the seed generator (`scripts/generate_seed.mjs`) drops
`claims_affected` entirely and reuses the same trimmed wording already used in
the production review PDF where needed for active items.

## Database schema

See `../supabase/migrations/0001_init.sql` for the full, commented SQL. Summary:

- **`review_responses`** — one row per `(report_version, review_id, reviewer_name)`, upserted on every save. Holds `decision`, `comment`, `resolved`, `created_at`, `updated_at`, `page_number`. A unique constraint on that triple means Steve's and the QA reviewer's answers never collide (different `reviewer_name`), and a future report version never overwrites this one (different `report_version`).
- **`review_response_history`** — append-only audit log, one row per save, populated automatically by a trigger. Never written to directly by the app.
- Row Level Security is enabled on both tables with **no policies** — default-deny. All access goes through the API routes using the `service_role` key server-side, which bypasses RLS by design. There is no anon-key path into this database at all.

## Authentication / access approach

No Supabase Auth, no account creation — this is one reviewer (plus a QA test identity), and account creation would be pure friction for no real security benefit at this scale. Instead:

1. Ramiro generates one long random token (`REVIEW_ACCESS_TOKEN`) for Steve and, optionally, a second one (`QA_ACCESS_TOKEN`) for dry-run testing — see `.env.example` for the generation command.
2. Steve is given a single private link: `https://<your-app>.vercel.app/?token=<REVIEW_ACCESS_TOKEN>`.
3. `src/middleware.js` validates the token on every request (including static assets like the page-preview PNGs and the report PDF — nothing is served unauthenticated), then sets a long-lived (`~6 months`) `httpOnly`, `Secure`, `SameSite=Lax` cookie and redirects to the clean URL (so the token never sits in browser history or a shared link after first use).
4. If the cookie is ever missing (new device, cleared cookies, cookie expired), `/login` provides a plain form to re-enter the token manually — no link re-issue required.
5. The QA token maps to `reviewer_name = "Ramiro QA"`, the real token maps to `"Steve"` — their answers are entirely separate rows, so dry-run testing can never contaminate or overwrite Steve's real review (or vice versa).

This is "simplest reliable" for a one-person private tool, not a general-purpose auth system: the threat model is a leaked link, not a sophisticated attacker, and the token is never logged, never in a URL after first visit, and HttpOnly (not readable by any injected script).

## Supabase setup

1. Create a Supabase project (or reuse an existing one Ramiro controls) at [supabase.com](https://supabase.com).
2. In the SQL Editor, run the entire contents of `../supabase/migrations/0001_init.sql` once. It's idempotent (`create table if not exists`, `create or replace function`, `drop trigger if exists` before each `create trigger`), so re-running it is safe if needed.
3. In **Project Settings → API**, copy the **Project URL** → `SUPABASE_URL`, and the **`service_role` secret key** → `SUPABASE_SERVICE_ROLE_KEY`. The service_role key is powerful (bypasses RLS) — treat it like a password; it only ever needs to exist as a server-side environment variable, never in client code, never committed.
4. No manual table creation through the dashboard UI is required — the migration file handles everything (tables, indexes, trigger functions, RLS).

## Environment variables

Copy `.env.example` to `.env.local` for local development, or set the same names in the Vercel project's **Settings → Environment Variables** for deployment. Required: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `REVIEW_ACCESS_TOKEN`. Optional: `QA_ACCESS_TOKEN` (recommended — keeps dry-run data separate).

## Report version

Hard-coded in `src/lib/constants.js`: `REPORT_VERSION = "SDA-ADMIN-2026"`. Every
database row and every export carries this. Per the project's versioning rule
(`../../00.project/changelog.md`), when a future report iteration needs its own
review pass, don't just bump this string in place — archive the current
`review_manifest.yaml` and this app's exported state into `90.archive/`, then
promote the new manifest into `02.content/` and update this constant to match.

## Running locally

```bash
cd 04.review/app
npm install
cp .env.example .env.local        # then fill in real values
npm run generate-seed              # writes src/data/review_items.json from 02.content/
npm run copy-assets                # copies page-preview PNGs + full report PDF
npm run dev                        # http://localhost:3000
```

(`npm run build` runs both generate/copy steps automatically via the `prebuild` script — the two manual commands above are only needed before `npm run dev`, since `next dev` doesn't run `prebuild`. Both scripts require `../../03.production/out/page_renders/` and `../../05.outputs/public/...` to already exist — run the production build first: `cd ../../03.production && python3 scripts/build.py --all`.)

Then open `http://localhost:3000/?token=<REVIEW_ACCESS_TOKEN>` once — it sets the cookie and redirects to `/`.

## Exports

Available from the completion screen (after all 5 items have a decision) as plain links — `GET /api/export/json`, `/api/export/csv`, `/api/export/decisions` — each authenticated by the same cookie, each reading live from Supabase at request time (so an export always reflects the current database state, not a cached snapshot). `DECISIONS.md` is formatted per item (`## Q# — Topic`, decision, comment, affected pages) with a header carrying the report title, version, reviewer, export timestamp, and summary counts.

## What this app deliberately does not do

- Does not integrate Steve's decisions back into the report — that's a separate, later task.
- Does not lock or "submit" the review — the completion screen is a summary view; every item stays reopenable indefinitely.
- Does not show claim IDs or evidence codes — this is commercial review, not technical/citation review.
- Does not require Steve to create an account, remember a password, or review any of the other 19 non-question pages (the optional "View full report" link exists for context only).
